## 0. Dominio vs mapeo HTTP

El dominio expone las tres operaciones con tipos primitivos. Los adapters HTTP las mapean 1:1 según AD-09 (spine-local); el dominio nunca ve headers, rutas ni objetos del framework. Decisión de dominio vs status HTTP: el dominio retorna `decision ALLOW|DENY`; el adapter mapea `ALLOW → 200 AuthorizeResponse` y todo `DENY` de política → `403 DenyBody` RFC-7807 con `decision: DENY` + `ExplanationDTO` obligatoria (PRD §5.2, ARCH §4.2/AD-01).

| Operación de dominio | Método HTTP canónico | Entrada HTTP | Salida HTTP |
| --- | --- | --- | --- |
| `resolveEffectivePermissions(userId: str, courseId: str, at: str)` | `POST /api/v1/authorize` + header `X-Academic-Subject-Context: <courseId>` | `{ user_id, resource_arn, action }` (sin `at`: el adapter captura `Clock.now()` una vez) | 200 `{ decision: ALLOW, effective_role, explanation }` o 403 `DenyBody { decision: DENY, explanation }` o error tipado |
| `revokeCourseAccess(userId: str, courseId: str)` | `POST /api/v1/subjects/{subject_id}/enrollments/{student_id}/drop` | `{ drop_reason }` | 200 `{ student_id, subject_id, status, revocation_propagated_at, explanation }` o error tipado |
| `ingestRoster(batch: RosterBatch)` | `POST /api/v1/subjects/{subject_id}/roster` | CSV (`institutional_id,email,full_name,assigned_role`, máx. 5.000.000 bytes, máx. 1000 filas) con `term` únicamente en query (`?term=`), o JSON equivalente con `term` únicamente en el body | 201 `{ processed, created_identities, updated_memberships, batch_id, explanation }` o 422 con manifiesto JSON + anexo CSV |

Contexto en rutas [ADOPTED 2026-10-13]: el header `X-Academic-Subject-Context` es obligatorio solo para `/authorize`; en revoke e ingest la fuente de `subject_id` es el path param canónico, sin exigir ni inferir header de contexto adicional; AD-01 no se extiende fuera de su alcance heredado en autorización.

Actor, token y rol administrativo [ADOPTED 2026-10-13, Ronda 6 Q1/Q2] (ADVF-01/02/03): el Bearer opaco se valida con el puerto `TokenVerifierPort` (adapter simulado con tokens de fixture; formato y firma reales fuera de alcance, identidad institucional simulada según AGENTS.md); devuelve `{actor_id, actor_role}` o falla → `401 AUTH_TOKEN_INVALID`. `revokeCourseAccess` e `ingestRoster` exigen `actor_role = admin` (rol institucional, distinto del rol de membresía): otro actor autenticado → `403 ADMIN_ROLE_REQUIRED`, después del 401 y antes de la sintaxis, sin mutación ni evento. Scheduler: `actor_id = 'system:scheduler'`, `actor_role = 'admin'`. Columnas NOT NULL del ledger: `actor_id`/`actor_role` del token; `resource_arn = urn:uai:subject:<subject_id>:model:*` para baja y lote; `action` = `revoke` (baja) / `ingest_roster` (lote); `action` de `/authorize` ∈ {`inference`, `training`} (Q5). Header repetido o vacío [ADOPTED 2026-10-13, estudiante] (H-24): se trata como ausente → `SUBJECT_CONTEXT_MISSING_OR_UNAUTHORIZED` (paso 3 del orden); se compara el valor del campo tal como lo entrega el parser HTTP (RFC 9110 excluye espacios de borde y no admite CRLF dentro); la app no normaliza nada más.

`userId` admite UUID (`identities.id`) o `institutional_id` (`STU-98432`, `TA-SOFIA-01`); el adapter lo resuelve a identidad canónica interna. Decisión [ADOPTED] 2026-10-13 (usuario, alcance: solo `institutional_id`): la comparación es case-sensitive exacta, sin case-folding ni conversión automática a mayúsculas (`stu-98432` no equivale a `STU-98432`); no se extiende a `courseId` (regla byte-a-byte adoptada aparte en §0). Formato UUID y espacios [ADOPTED 2026-10-13]: UUID aceptado solo en forma canónica con guiones `8-4-4-4-12`; dígitos hex en mayúscula o minúscula aceptados y normalizados a la representación canónica en minúscula para la búsqueda. Se rechazan llaves, URN, forma sin guiones, whitespace externo/interno y caracteres de control; sin `strip`. Si no es UUID canónico, se intenta `institutional_id` con comparación exacta y gramática `^[A-Za-z0-9-]{1,64}$`, case-sensitive exacta (Q7, ADVF-21 [ADOPTED 2026-10-13]); si no resuelve → `UNKNOWN_IDENTITY` existente, sin códigos nuevos. Regla [ADOPTED] 2026-10-13 para `courseId` (AD-01 heredado, `planning/ARCHITECTURE.md` l.329-331, sin modificar): el subject extraído del ARN se compara byte-a-byte con el valor crudo de `X-Academic-Subject-Context`, sin `strip`, `upper` ni otra normalización; si difieren —incluido por mayúsculas/minúsculas— hay mismatch y se deniega (`RESOURCE_SUBJECT_MISMATCH`, 403). La normalización propuesta queda retirada como alternativa válida. Las grafías minúsculas de los ejemplos del PRD/ARCH no tienen valor normativo. `at` y reloj [ADOPTED 2026-10-13, corrección usuario]: el endpoint público `/authorize` no acepta `at` en el body. El adapter captura `Clock.now()` una sola vez por solicitud (`request_now`) y usa ese instante para la evaluación en vivo. La operación de dominio conserva el parámetro `at` de Annex A como entrada interna para pruebas y replay: ese valor puede ser histórico y nunca es controlado por el cliente. `request_now` se reutiliza para timestamps administrativos y `occurredAt`; el worker usa el timestamp del evento y nunca llama a `Clock.now()` para reconstruirlo.

## 2. `revokeCourseAccess(userId, courseId)`

- **Nota de firma** [ADOPTED 2026-10-14, estudiante] (R8-10, acepta R7-01): la firma Annex A `revokeCourseAccess(userId, courseId)` es la operación conceptual; el servicio de dominio recibe además, como parámetros explícitos, `actor`, `drop_reason`, `timestamp` y `request_now`, para que la validación P3/P4 sea función pura testeable con `fake_clock`. El adapter HTTP solo parsea.
- **Capa:** puerto inbound Revoke → `domain/membership` → puertos `MembershipStore`, `CredentialStore`, `LedgerWriter`, `Clock`.
- **P:**
  - P0 (Q1 [ADOPTED 2026-10-13], ADVF-01): actor con `actor_role = admin` (token vía `TokenVerifierPort`); si no → `403 ADMIN_ROLE_REQUIRED` (ErrorBody, sin ExplanationDTO), sin mutación ni evento.
  - P1: identidad y curso existen (misma resolución que §1) → violación: `UNKNOWN_IDENTITY` / `UNKNOWN_COURSE`, 404.
  - P2: existe membresía del par en estado `ACTIVE` o `DROPPED` (como máximo una `ACTIVE` por par por el índice parcial de Q3; la baja no recibe `term`) → si nunca existió: `MEMBERSHIP_NOT_FOUND`, 404; si está `SUSPENDED`/`COMPLETED`: `INVALID_TRANSITION`, 409 (`COMPLETED` = no activa; ninguna de las tres operaciones la crea [ADOPTED 2026-10-13, estudiante]).
  - P3: `drop_reason` string de 1–280 puntos de código Unicode (no bytes UTF-8 ni grapheme clusters), sin normalizar Unicode; caracteres de control (categoría Unicode `Cc`) → `MALFORMED_DROP_REASON` 400 (ECF-12 [ADOPTED 2026-10-13, Ronda 6]); "solo espacios" = todos los caracteres son blancos Unicode (`str.isspace()`), así `" \t\n "` → `400 MALFORMED_DROP_REASON`; si contiene un secreto `uai_live_…`, se enmascara antes de persistir, loguear o responder — AD-06 (heredado) gana sobre "original intacto" [ADOPTED 2026-10-13, estudiante] (H-19); en valores válidos sin secreto se conserva el texto original → violación: `MALFORMED_DROP_REASON`, 400.
